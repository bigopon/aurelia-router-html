Nested Routers

Create a local router boundary when one screen needs its own route state without taking over the browser URL.

Syntax

<au-route path="workspace" exact>
  <workspace-shell>
    <au-router current-path.bind="panelPath">
      <au-route path="list" exact>List</au-route>
      <au-route path="detail/:id" exact>Detail</au-route>
    </au-router>
  </workspace-shell>
</au-route>

Meaning

au-router starts a new route tree for the au-route and au-link declarations inside it. That inner tree has its own root context, coordinator, active matches, navigation lifecycle, and memory-backed path adapter.

The current first step is intentionally memory-only. No mode selection, hash ownership, query-key ownership, or delegated pathname slicing is required to use it.

Apply it

Use it for tab panels, inspectors, side-by-side workspaces, setup flows, or embedded tools that need route-driven UI state while the outer application keeps ownership of the browser URL.

current-path is the integration point: write a nested route location to request navigation, and read the committed nested location back after redirects, guards, or local recovery settle.

Use current-path as the boundary state

<au-router current-path.bind="panelPath">
  <au-route path="drafts" exact>Drafts</au-route>
  <au-route path="drafts/:id" exact>Editor</au-route>
</au-router>

The bound value is the nested router's own location, for example /drafts/42?tab=history#diff. External writes request normal router navigation. Successful navigation writes the committed destination back. Rejected navigation restores the previous committed value.

Keep outer and inner ownership separate

<au-route path="workspace" exact>
  <au-router current-path.bind="panelPath">...</au-router>
</au-route>

The outer route still owns the browser URL, title, scrolling, and focus behavior. The nested router owns only its internal route location. A nested router should not reinterpret deployment basePath configuration as its composition API.

Route-graph note

Future public introspection should not assume a single active route chain inside a router. Match-all siblings, pathless groups, and local fallback rematching can create multiple active branches. A flat active-match view and a branch view fit the model better.

Next steps, not current API

Hash-backed, query-backed, pathname-sliced, or custom-adapter nested routers remain follow-up work. Those extensions need explicit slot ownership and rollback rules so nested routing never ambiguously shares browser location state.
