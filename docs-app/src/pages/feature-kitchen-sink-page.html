Kitchen Sink

Build a tiny playroom app by mixing normal Aurelia templates with a declarative route tree.

Syntax

<au-route path="workspace" can-load.bind="requireSession()">
  <let sessionLabel.bind="currentUser.name + ' · ' + currentUser.role"></let>
  <workspace-shell>
    <strong au-slot="title">Aurora Ops workspace</strong>
    <span au-slot="subtitle">${sessionLabel}</span>

    <template repeat.for="user of users">
      <au-route path.bind="'users/' + user.id" exact>
        ...
      </au-route>
    </template>
  </workspace-shell>
</au-route>

Meaning

This example treats Router HTML as normal application structure rather than a narrow routing demo. A mock in-memory database, sign-in state, nested routes, repeated route declarations, CRUD forms, route guards, and slotted shells all share the same Aurelia scope.

Repeat items, <let> variables, VM properties, projected slots, and form bindings remain available inside matched branches, so the routed app still reads like ordinary Aurelia markup.

Apply it

Use this style when you want the route tree to stay close to real product markup. Keep each route beside the form, list, or shell it controls; use repeated routes when records come from data; and let the view-model own application state such as sessions, drafts, and mock persistence.
