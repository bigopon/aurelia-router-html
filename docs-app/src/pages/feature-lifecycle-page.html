Route Lifecycle

Use one lifecycle for route entry, fresh-view replacement, and in-place reruns.

Syntax

<au-route
  path="products/:id"
  transition-on="params query"
  transition-plan="rerun"
  can-load.bind="transition => canOpenProduct(transition)"
  loading.bind="loadProduct($lifecycle)"
  loaded.bind="productIsReady($lifecycle)">
  <h1>${$route.data.loading.name}</h1>
</au-route>

The router evaluates each Aurelia expression at its lifecycle phase in the route's live binding scope. The same bindings serve initial entry and any matched-route transition selected by the declaration.

Meaning

can-load approves, cancels, or redirects. loading prepares the route and waits for a returned promise. loaded runs after entry or replacement activation, or after the retained nested branch finishes its rerun.

Nested branches load from parent to child and report loaded from child to parent. This lets a parent prepare shared data first while its loaded callback observes a complete child branch.

The fulfilled return values are available as $route.data.loading and $route.data.loaded. The router does not cache them: applications decide whether to reuse context.previousData, a service cache, or a fresh request.

Choose what happens when the route stays matched

<au-route
  path="products/:id"
  transition-on="params query"
  transition-plan="rerun"
  can-load.bind="transition => canOpenProduct(transition)"
  loading.bind="loadProduct($lifecycle)"
  loaded.bind="productIsReady($lifecycle)">
  <product-detail product.bind="$route.data.loading"></product-detail>
</au-route>

transition-on accepts params, query, hash, all, or none. Combine params, query, and hash with spaces or commas; use all and none only as standalone values. It defaults to params.

transition-plan="rerun" is the default. It preserves the component, controller, view, and DOM nodes while running can-load, loading, and loaded again. replace runs can-unload, prepares the candidate through the normal load lifecycle, and swaps in a fresh view. none only updates the reactive route values.

Every affected guard on an already-declared route approves before selected transitions begin loading or change the rendered tree. Descendants created inside a fresh replacement run their normal entry guards as the candidate activates; denial or failure still rolls back the complete replacement. Call $route.reload() to force the configured plan at the current location, or $route.reload({ plan: 'replace' }) to override it once.

Apply it

export class App {
  public loadProduct(context: RouteLifecycleContext) {
    return this.products.get(context.params.id, context.signal);
  }

  public productIsReady(context: RouteLifecycleContext) {
    return this.analytics.pageReady(context.kind, context.to);
  }
}

The lifecycle context has kind: 'enter' | 'replace' | 'rerun', immutable from, to, and changes values, destination params, query and hash, the route, abort signal, and prior lifecycle results. from is null on entry. changes lists every actual URL-state difference, not only the input that triggered the plan. Return any value or promise; activation waits only for promises.

Lifecycle errors

A thrown or rejected can-load or loading callback stops the pass before loaded. It prevents entry or replacement activation, and aborts an in-place rerun before its completion callback. A loaded failure happens later, after the view has activated or rerun loading has completed, but still fails the navigation. Handle expected data failures inside the callback when the page should present a recoverable error state.

The navigation transaction keeps the outgoing URL and view available while loading is pending. A failed rerun keeps the existing view and DOM mounted while restoring the prior route values and lifecycle data. A failed replacement removes its candidate view and reactivates the prior view. Unless an error boundary recovers or redirects, programmatic navigation rejects with the original error.

Cancelled and unhandled failed navigations restore $route.data to its pre-navigation values. When an error boundary locally recovers by replacing a failed subtree with a sibling fallback, that failed route context may retain its last fulfilled lifecycle result. This is route state for previousData, not router-managed caching; applications must not rely on local recovery to clear it.
